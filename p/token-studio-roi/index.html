项目地址：GitHub - Token Studio ROI
npm 包：token-studio
Release：v6.0.8
动图体验：Token Studio Walkthrough

npx token-studio

Token Studio 不是一个云端 SaaS，也不是在线账单系统。它的核心前提是：AI 编程数据应该先留在本地。

它读取本机 Claude Code、Codex CLI 等工具日志里的结构化 token 元数据，写入本地 SQLite，再在浏览器和桌面 Pulse 里做复盘。

1. 为什么要做这个项目

我一开始只是想知道自己用了多少 token。

但做着做着发现，单纯的 token 数字其实不够用。

比如：

  • 今天用了几千万 token，到底是花在功能开发、调试修复，还是无效探索？
  • 重模型是不是被用在了测试验证、上下文整理这种低价值任务上？
  • 某个项目成本很高，它最后有没有 PR、commit、文档、部署或可展示产出？
  • 如果下周继续这样用模型，会不会只是把更多 token 花在重复上下文和低价值试错上？

普通 token dashboard 主要回答“用了多少”。
但我真正想回答的是：

这些 token 花在哪，换来了什么，下周怎么少花一点做更高价值的事？

所以 Token Studio 的定位不是 token meter，而是：

本地隐私优先的 AI 编程投入复盘系统。

2. 它现在能做什么

Token Studio 当前围绕一条闭环设计：

真实本地 token
  -> 可信覆盖
  -> 自动证据
  -> ROI 复盘
  -> 模型策略
  -> 行动报告

它主要有六个部分。

2.1 真实本地采集

Token Studio 会读取本机仍然存在、且带有可靠 token 字段的结构化日志。

目前核心可信来源是：

  • Claude Code
  • Codex CLI

它不会保存 prompt 正文、response 正文、transcript、diff，也不会保存完整本机路径。采集重点是：

  • source
  • model
  • session
  • timestamp
  • input tokens
  • output tokens
  • cache tokens
  • reasoning tokens

也就是说，它关心的是结构化使用元数据，不是你的对话内容。

2.2 官方公开价换算

项目里有一套官方公开 token 价格换算逻辑。

这里必须说清楚：
Token Studio 里的美元金额不是供应商账单，也不是财务对账凭证。

它只是把 token 使用量按 OpenAI、Anthropic 等公开价格口径换算成一个复盘指标，用来比较模型策略、项目成本和趋势。

未公开美元价的模型不会被硬算成 $0，也不会编造价格，而是标记为未定价。

2.3 Coverage Trust

很多工具会在本机留下目录或日志，但这不等于一定能采到 token。

所以 Token Studio 把来源分成几类：

  • 原生可信采集
  • ccusage 可导入
  • 实验采集
  • 仅检测到
  • 无可靠 token 字段 / 不支持

这个设计是为了避免一种很危险的错觉：

检测到了工具目录，就以为已经覆盖了用量。

我宁愿它告诉用户“这个来源现在没有可靠 token 字段”，也不希望它用文本长度估算 token，然后给出看似完整但实际不可信的数据。

2.4 Evidence Flywheel

采到 token 之后，还不够。

真正有复盘价值的是：这些 token 对应了什么工作？

所以 Token Studio 增加了证据层：

  • 项目
  • 任务类型
  • 工作目的
  • 工作阶段
  • 产出状态
  • 产出价值
  • 产出链接
  • 人工确认 / 自动推断 / 待确认草稿

这就是 Evidence Flywheel。

它把 token 从“消耗数字”变成“工作证据”。

比如一个 session 可以变成：

项目：Token Studio ROI
任务：功能开发
阶段：实现
产出状态：已完成
产出：commit / PR / 文档
价值：中 / 高
证据来源：自动高置信或人工确认

这样 /review 才能继续判断：

  • 哪些 token 产出了东西？
  • 哪些高成本 session 还没归因？
  • 哪些任务可以降级模型？
  • 哪些上下文输入过重？
  • 哪些建议应该进入下周行动清单？

2.5 ROI Advisor 和 Savings Simulator

Token Studio 不调用 LLM 来生成建议，原因很简单：
这个工具本身就是为了帮我少花 token，不应该为了分析 token 再消耗一轮 token。

所以它采用本地规则引擎。

典型规则包括：

  • 高成本未归因 session：先补证据
  • 测试验证、探索、上下文整理使用重模型：建议切到轻量模型
  • 低价值或已废弃任务使用高成本模型：建议先轻量试错
  • 高 input / low output：建议压缩上下文
  • cache 复用低且 input 高：建议沉淀项目上下文
  • 未定价模型：不纳入美元节省判断

Savings Simulator 也不声称真实节省金额，只做官方价换算下的策略模拟。

它回答的是：

如果这类低价值 / 探索 / 测试任务从重模型切到轻量或中等模型，按官方价口径可能少花多少？

2.6 Desktop Pulse

v6 增加了一个桌面 Pulse 伴侣。

它不是主产品，也不替代浏览器工作台。

浏览器里的 Dashboard、Trust、Review 才是完整复盘入口。
桌面 Pulse 的作用更轻：

  • 看最近 24 小时 token
  • 看近窗口 burn rate
  • 看官方价换算成本
  • 看输入 / 输出 / cache
  • 看模型消耗分布
  • 看预算 guardrail
  • 快速打开看板和复盘页

它更像一个本地实时仪表盘，而不是完整分析后台。

3. 当前体验

启动命令：

npx token-studio

默认流程是：

只读 coverage
  -> 可信 Claude/Codex event 级采集
  -> 写入本地 SQLite
  -> 启动本地 Web/API
  -> 打开浏览器看板
  -> 后台定时刷新可信 token 元数据

3.1 看板：先看成本、模型和趋势

Dashboard 主要负责回答三个问题：

  • 本期总 token、输入、输出、缓存、推理 token 是多少？
  • 官方公开价换算成本大概是多少？
  • 这些消耗主要来自哪些模型、来源和项目？

我把图表和核心 KPI 放在最前面，是因为用户打开以后最先关心的不是功能说明，而是：

我的数据到底是多少？趋势是否异常？哪个模型最贵？

3.2 Trust：确认数据是不是真实可信

Trust 页面负责回答：

  • 当前是 demo、空库、旧聚合库，还是真实 event 级数据？
  • Claude / Codex / Cursor 等来源分别是什么状态？
  • 哪些来源可用于 ROI 复盘？
  • 哪些来源只是 detected-only，不能当成真实覆盖？
  • daily / session / event 之间是否能对齐？

这一步很重要。
因为如果数据来源不可信，后面的 ROI 分析就没有意义。

3.3 Review：把 token 变成 ROI 证据

Review 页面不是普通报表，而是复盘页。

它关心：

  • 哪些 token 已经有产出证据？
  • 哪些 session 仍然缺项目、任务、阶段、价值或产出？
  • 哪些模型策略可以调整？
  • 哪些高成本任务下周需要改做法？
  • 哪些建议应该加入行动清单？

我还加了专业可复制输出包：

  • 复盘证据包
  • 技术博客草稿
  • 简历 / 面试项目描述

这些不是几句静态文案，而是基于当前结构化数据生成的 Markdown 内容，方便直接复制到周报、博客或简历项目说明里。

3.4 Desktop Pulse：桌面实时伴侣

Desktop Pulse 是 v6 的桌面端补强。

它的意义不是替代浏览器，而是解决另一个问题：

我不想一直开着浏览器 tab，但想随时知道今天 token 是否失控。

Pulse 重点展示：

  • 近 24 小时 token
  • 近 24 小时官方价换算
  • 请求数
  • 输入 / 输出 / cache
  • 模型消耗 Top
  • 来源分布
  • Agent 服务时长
  • 当前建议

桌面端只读本地数据，不上传，不重新实现采集，不保存正文。

4. 架构设计

Token Studio 的架构很简单，但每一层都尽量保持边界清楚。

Claude Code / Codex CLI 本地日志
        |
        v
结构化 collector
        |
        v
SQLite: token_events / session_usage / daily_usage
        |
        v
Coverage Trust / Reconciliation
        |
        v
Evidence Flywheel
        |
        v
Dashboard / Trust / Review / Live / Desktop Pulse

4.1 为什么用 SQLite

因为这是个人本地工具。

SQLite 的优点很直接：

  • 不需要部署数据库
  • 容易备份
  • 适合本地单用户
  • 和 Node.js 24 的 node:sqlite 能很好结合
  • 数据文件可以明确排除在 npm 包和 Git 仓库之外

4.2 为什么不直接做云端

因为这个项目处理的是 AI 编程工作流数据。

即便不保存正文，session、模型、时间、项目名、产出链接也可能透露工作节奏和项目方向。

所以默认选择是：

数据留在本地，复盘也在本地完成。

如果未来要做云同步，那会是另一个产品，而不是当前 Token Studio 的自然延伸。

4.3 为什么不估算所有工具

竞品里很多工具覆盖范围很广，比如 ccusage、CodeBurn、TokenTracker、tokscale。

Token Studio 没有选择为了覆盖数量去伪造数据。

原因是：
如果一个工具本地没有可靠 token 字段，只靠文本长度估算，那看起来覆盖了，实际会破坏信任。

所以 Token Studio 的策略是：

  • Claude / Codex：优先做原生可信采集
  • ccusage：作为结构化 JSON bridge
  • Cursor / Cline / Copilot 等：没有可靠 token 字段时只显示 detected-only 或建议导入
  • 未定价模型：不参与美元节省判断

5. 隐私和安全边界

这个项目里我最重视的一点是：不要为了做复盘，把更敏感的数据收集进来。

Token Studio 明确不保存：

  • prompt
  • response
  • transcript
  • diff
  • 完整本机路径
  • 文件内容
  • 命令正文

Web API 默认只绑定本机地址。
普通写接口需要 local Origin + JSON。
/api/ingest 默认关闭，只有设置 INGEST_TOKEN 后才启用 Bearer token 写入。

Electron Desktop Pulse 也只是 companion：

  • 不上传数据
  • 不重新实现采集
  • 不读取正文
  • 只通过本地 API 读取聚合后的 token 元数据
  • 不把桌面端变成远程控制面板

这部分参考了 Electron 官方安全建议：禁用不必要的 Node 集成、限制远程内容、收紧窗口和权限边界。

6. 它和 ccusage、CodeBurn、TokenTracker 有什么不同

这些竞品都很强，而且很多地方值得学习。

工具强项Token Studio 的差异
ccusage多来源覆盖、JSON 报表成熟Token Studio 更关注 ROI evidence、项目/产出归因和复盘报告
CodeBurnTUI、本地成本观测、工具覆盖Token Studio 更关注可信覆盖、证据链和模型策略
TokenTracker多工具、桌面组件、去重Token Studio 更关注本地工作证据和下周行动
tokscaleCLI/TUI、可视化和 leaderboardToken Studio 不做排行榜，优先做个人 ROI 复盘

所以 Token Studio 不试图替代所有工具。

它更像是一个本地复盘层：

统计工具告诉你用了多少；Token Studio 追问这些 token 换来了什么。

7. 我怎么判断这个项目是否有价值

我不想把这个项目写成“又一个全能平台”。

更准确地说，它解决的是一个很具体的问题：

对高频 AI 编程用户来说，token 已经变成持续投入，但缺少一个本地、可信、可复盘的投入产出系统。

如果只看 token 数，意义有限。
如果 token 能连接到项目、任务、阶段、产出和模型策略，它才开始变成可管理的工作资产。

这个判断也符合软件工程研究里常见的问题-方法-证据-评价结构：
先定义真实问题，再做可运行系统，然后用真实数据、限制条件和验收门来评价，而不是只做一个漂亮页面。

Token Studio 的结果不是“自动证明 ROI 提升了多少”。
它更保守：

  • 哪些数据可信
  • 哪些只能看趋势
  • 哪些不能下结论
  • 哪些证据缺口最值得补
  • 哪些模型策略值得下周试

这比编造一个“节省 37% 成本”的结论更可靠。

8. 我给这个项目的定位

我现在会把 Token Studio 定位成：

本地 AI 编程投入复盘系统。

不是：

  • 精确账单系统
  • 云同步平台
  • 团队管理后台
  • 多用户 SaaS
  • token leaderboard
  • 大而全 collector
  • 自动理解代码内容的 AI 评审系统

它的护城河是：

  • 本地隐私
  • 真实结构化 token
  • 可信覆盖解释
  • 自动证据队列
  • ROI 复盘
  • 模型策略
  • 行动报告

9. 当前局限

这个项目也有明显边界。

第一，它不能恢复所有历史。
它只能覆盖本机仍然保留、且日志里有可靠 token 字段的历史数据。

第二，它不是供应商账单。
官方价换算适合做趋势和策略复盘，不适合做财务对账。

第三，它不会读取正文，所以不会自动理解任务质量。
产出价值仍然需要人工确认或结构化证据支撑。

第四，它不会为了覆盖面伪造 token。
如果某个工具没有稳定 token 字段，就不会写成“已采集成功”。

第五，桌面 Pulse 只是伴侣。
真正的复盘仍然在浏览器 Review 和 Trust 页面里完成。

10. 后续是否继续做

v6 之后，我不打算继续无限追竞品功能。

后续只维护几类事情：

  • 上游日志格式变化
  • 官方价格变化
  • 真实 bug
  • 隐私和安全问题
  • release / npm / 桌面打包问题

明确不做：

  • 云同步
  • 账号体系
  • 多用户
  • leaderboard
  • 大型 TUI
  • 伪造 collector
  • 文本长度估算 token

因为再往后加功能，收益已经不如把当前闭环打磨稳定。
